# pi-context-vault v0.2.0 release candidate

> **Status: RELEASE CANDIDATE / UNTAGGED.** This document describes the v0.2.0 metadata on current `main`. No
> immutable `v0.2.0` tag or release has been created. The latest immutable tag remains `v0.1.2`.

## Major changes since v0.1.2

- Repository-map capsules are frozen per user turn and explicitly labeled as snapshots, preventing repeated LLM calls
  in one turn from re-querying or silently changing the injected map.
- Repository-map generations are bounded, file outcomes distinguish unsupported and failed indexing, and cached map
  search plus hot-path telemetry reduce and expose repeated work.
- Observation archiving has configurable policies, UTF-8-safe bounded retrieval, and append-only incremental metadata
  persistence.
- File locking and atomic publication are hardened against recovery races and transient Windows inspection/publication
  errors.
- Runtime telemetry and a no-token ablation harness add reproducible plan/run/verify/analyze mechanics without making
  the extension depend on provider access during package smoke.

## Version and persisted-map compatibility

Package metadata and the model-visible status use `0.2.0`. Repo Map provenance continues to use
`generatorVersion: "0.1.0"` intentionally: that field versions the persisted map format, not the npm package. This
release bump does not make existing compatible generations invalid. The generator version should change only when a
persisted-format incompatibility requires rejection or migration.

## Installation status

For an immutable installation today, use the actual latest tag:

```bash
pi install git:github.com/Fubuyunhua/pi-context-vault@v0.1.2
```

To evaluate this untagged release candidate, review a `main` checkout, run `npm ci`, and load
`extensions/index.ts` with Pi's `-e` option. Do not use an `@v0.2.0` install source unless and until that immutable tag
is created.

and push the immutable `v0.2.0` tag, verify installation from that exact tag, publish the release, and only then update
