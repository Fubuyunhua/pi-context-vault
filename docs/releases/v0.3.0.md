# pi-context-vault v0.3.0 release candidate

> **Status: RELEASE CANDIDATE / UNPUBLISHED.** No release date is assigned. No immutable `v0.3.0` tag, package
> publication, or release is claimed by this document. This pre-1.0 breaking minor bump follows removal of all Repo
> functionality from Context Vault.

## Vault-only scope and surfaces

This candidate is observation-only: recoverable Observation archival, bounded receipts and get/search, context-pressure
reduction, Vault status/doctor, and Vault artifact retention. Its exact Tools are `context_vault_obs_get`,
`context_vault_obs_search`, and `context_vault_status`. Its exact command is `/context-vault`, with `status`,
`status-json`, `gc`, `doctor`, and `rebuild` subcommands.

`/context-vault rebuild` is an inert compatibility stub and returns exactly:

```text
Repository rebuild has moved to pi-repo-context.
Install pi-repo-context and use /repo-context rebuild.
```

For one post-split compatibility period, `.pi/context-vault.json` tolerates and ignores these eight legacy keys while
warning that Repo Map moved: `repoMapEnabled`, `mapInjectionMode`, `mapContextMaxBytes`, `mapDebounceMs`,
`mapGenerationRetention`, `mapQuotaBytes`, `mapExcludePatterns`, and `debugRequestFingerprints`. Unknown nonlegacy keys
remain errors.

`/context-vault gc` operates only on Vault artifacts and metadata. Vault state remains exactly under
`${PI_CODING_AGENT_DIR}/context-vault/projects/<projectId>/artifacts` and `metadata`; GC never reads or removes legacy
Repo Map or new Repo Context state.

## Split migration and compatibility

No Repo Context release is claimed here. Only if its independently reviewed immutable `v0.1.0` tag exists may users
install it with:

```bash
pi install git:github.com/Fubuyunhua/pi-repo-context@v0.1.0
```

After that conditional release, use `repo_context_search`. `context_vault_repo_map` → `repo_context_search` is a
deprecated Repo Context `0.1.x`-only alias, planned for removal in Repo Context `0.2.0`; Context Vault owns neither
repository Tool.

Repo Context never reads the old `.pi/context-vault.json`. Copy supported settings manually into
`.pi/repo-context.json`: `repoMapEnabled` → `enabled`, `mapContextMaxBytes` → `searchMaxBytes`, `mapDebounceMs` →
`debounceMs`, `mapGenerationRetention` → `generationRetention`, `mapQuotaBytes` → `quotaBytes`, and
`mapExcludePatterns` → `excludePatterns`. `mapInjectionMode` and `debugRequestFingerprints` have no replacement.
Repo Context starts cold from source into its own `${PI_CODING_AGENT_DIR}/pi-repo-context/projects/<projectId>` root.
Neither product reads, migrates, adopts, collects, or deletes legacy
`${PI_CODING_AGENT_DIR}/context-vault/projects/<projectId>/repo-map` state.

Before starting Repo Context beside a pre-split Vault, set `repoMapEnabled: false` and `mapInjectionMode: "off"`, stop
Pi, and restart into a new session. Running both repository implementations concurrently is unsupported.

Ownership remains distinct: Context Vault owns extension ID/UI key `context-vault`, `context_vault_status`, and Vault
telemetry; Repo Context owns extension ID/UI key `repo-context`, `repo_context_status`, and Repo telemetry. Neither
product shares status or telemetry state. There is no automatic repository context injection. This candidate ships no
paused S03 Planner/Renderer/Projection Cache work and no bench or gold-task assets.

## Rollback and residual risk

Rollback requires no state conversion: stop/disable Repo Context, restart Pi, and use the reviewed pre-split checkpoint
only if legacy repository behavior is required. Do not delete either state root or Observation evidence.

Vault revalidates its owned namespace and uses no-follow regular-file handles where supported. Node has no portable
`openat` API, so a privileged local process that races an ancestor rename between validation and access remains a
residual TOCTOU risk.
